## 0. Executive Summary and Business Model

We are building **three simple casual/hyper-casual games** for killing time, whose sole revenue source is **In-App Ads**. No login, no server, no player data stored in the cloud — everything is local.

| Item | Decision |
|---|---|
| Platforms | Android + iOS (from the same Flutter codebase) |
| Languages | English (source) + Arabic (full RTL) |
| Revenue model | Ads only: Interstitial + Rewarded + Banner + App-Open |
| Login | **None** — local storage only |
| Categories | Puzzle (Blocko, Mergo) + Arcade (Dashy) — the two highest-earning ad categories |
| Design philosophy | One tap/one swipe, short sessions, instant restart = the highest possible number of ad impressions |
| State | **GetX** (controllers + services + bindings + routing) |
| Art assets | Cheerful cartoon style, each game has a mascot with a smiling face |

**The economic principle:** Revenue = (number of players) × (number of sessions) × (ad impressions per session) × (eCPM). Our design maximizes "ad impressions per session" through fast death/restart loops, while keeping the game fun so that churn does not increase.

---

## 1. Locked Decisions — do not change them

1. **A single monorepo** managed with **Melos**: a shared `game_core` package + each game as a standalone app under `apps/`.
2. **Flutter + GetX** for all games. The arcade game (Dashy) uses **Flame** on top of Flutter for the game loop/physics. Blocko and Mergo are built with **pure Flutter** (`CustomPainter` + `AnimationController`) inside GetX.
3. **No login.** Local storage via **Hive** (structured) + `shared_preferences` for simple flags.
4. **Ads:** Start with **Google AdMob** (`google_mobile_ads`) for the MVP, then enable **AppLovin MAX mediation** when scaling up. All ad logic is isolated in `AdService` inside `game_core` so that switching networks never touches gameplay code.
5. **Currency:** A single currency, `coins`, spent on **cosmetic skins only** (no gameplay effect — purely cosmetic). No IAP in the MVP (leave an empty `IapService` interface as a future placeholder for a "Remove Ads" button).
6. **Privacy:** Implement **Google UMP (consent)** + **ATT (iOS)** before loading any ad. Do not collect any PII.
7. **Performance:** 60fps target, base APK/IPA size < 40MB per game (more downloads = more ads).

### 3.2 Bootstrap and GetX (App Bootstrap)

Every game's `main.dart` calls a shared bootstrap function and then runs `GetMaterialApp`.

```dart
// game_core: src/app/bootstrap.dart
Future<void> bootstrapGame({required GameConfig config}) async {
  WidgetsFlutterBinding.ensureInitialized();
  await HiveService.init();                    // local stores
  await Get.putAsync(() => AudioService().init());
  Get.put(AnalyticsService()..init());
  Get.put(AdService(config.adUnits)..init()); // preloads ads
  Get.put(CoinsController());
  Get.put(ConsentController());                // UMP + ATT
}

// apps/blocko/main.dart
void main() async {
  await bootstrapGame(config: blockoConfig);
  runApp(GetMaterialApp(
    title: 'Blocko',
    translations: BlockoTranslations(),        // + CommonTranslations
    locale: LocaleController.saved,            // persists the user's choice
    fallbackLocale: const Locale('en'),
    supportedLocales: const [Locale('en'), Locale('ar')],
    theme: GameTheme.blocko,
    getPages: BlockoRoutes.pages,
    initialRoute: Routes.splash,
  ));
}
```

### 3.5 The Ad Service `AdService` (The Revenue Core — Implement It Precisely)

**Ad types used:**

| Type | Where | Monetization purpose |
|---|---|---|
| **App-Open** | On cold start + on return from background | Guaranteed high-value impression |
| **Interstitial** | After Game Over (with constraints) | The largest share of revenue |
| **Rewarded** | Continue/Revive, Double coins, Unlock skin, Undo/Hint, Booster | Highest eCPM, opt-in |
| **Banner** | Only at the bottom of menu screens (not during gameplay) | Steady background income |

**Service interface:**

```dart
class AdService extends GetxService {
  final AdUnits units;                          // per-platform ids from GameConfig
  final consent = Get.find<ConsentController>();

  Future<AdService> init() async {
    await MobileAds.instance.initialize();
    await consent.ensure();                      // UMP + ATT before loading
    _preloadInterstitial(); _preloadRewarded(); _preloadAppOpen();
    return this;
  }

  // Interstitial — with frequency capping (see 3.6)
  Future<void> maybeShowInterstitial({required String placement}) async {...}

  // Rewarded — returns a result: did the user watch the full ad?
  Future<bool> showRewarded({required String placement}) async {...}

  Widget bannerWidget();                         // for use in menus only
  Future<void> showAppOpenIfAvailable() async {...}
}
```

**Mandatory rules:**

- **Preload** the next ad as soon as the current one closes — never make the player wait.
- **Do not show an Interstitial during active gameplay**, only at natural transition points (Game Over).
- **No Banner during gameplay** (policy + it prevents accidental clicks).
- Every call passes a `placement` (string) for analytics (such as `game_over`, `revive`, `double_coins`).
- **Test IDs during development** (Google's official ones):
  - AppOpen: `ca-app-pub-3940256099942544/9257395921`
  - Interstitial: `ca-app-pub-3940256099942544/1033173712`
  - Rewarded: `ca-app-pub-3940256099942544/5224354917`
  - Banner: `ca-app-pub-3940256099942544/6300978111`
  - **Replace them with the real IDs before release**, and place them in `GameConfig.adUnits` for each platform.

### 3.6 Ad Frequency Policy (Frequency Capping — balancing revenue against churn)

The `maybeShowInterstitial` logic shows the ad only if **all** of the following hold:

1. At least **`minInterstitialGapSeconds` = 45s** have passed since the last Interstitial (store `lastInterstitialAt`).
2. `gameOverCounter % interstitialEveryNGameOvers == 0` where **N = 2** (every second Game Over).
3. The player is **not** in their very first session (do not disturb a new user during the first 30–60 seconds — grace period).
4. No App-Open ad was shown within the last 15 seconds.

Tunable values in `GameConfig.adPolicy` (for A/B testing later):

```dart
adPolicy: AdPolicy(
  minInterstitialGapSeconds: 45,
  interstitialEveryNGameOvers: 2,
  firstSessionGraceSeconds: 60,
  appOpenColdStart: true,
  appOpenOnResume: true,
)
```

### 3.8 Full Sensory Design (Game Feel / Juice — The Heart of Addictiveness)

> **Golden rule:** the difference between an ordinary game and an addictive one is not the rules, but the **feel**: every action must be rewarded immediately — visually, audibly, and haptically at the same time (< 100ms). This section is mandatory, not decoration.

**a) Audio (`AudioService`) — pleasant and satisfying:**

- Short, clean SFX (< 300ms), pitch-tuned (mixed/normalized) so they are not annoying on repetition.
- **Pitch-rising on streaks:** each consecutive combo/merge rises one step in pitch (do-re-mi-fa...) — this creates an "escalating auditory pleasure" that drives the player to continue.
- Sounds required for every game: `tap`, `success`, `clear/merge`, `combo_1..5` (ascending tones), `coin` (a golden chime), `record` (a short fanfare), `game_over` (a gentle, non-discouraging descending tone), `button` (a soft click), `whoosh`.
- Light, cheerful background music (loop) that can be muted, at a low level that does not overpower the SFX.
- All audio respects the Sound/Music settings in Hive.

**b) Haptics (`HapticsService`) — pulls the player in:** specific patterns per event:

| Event | Pattern |
|---|---|
| Successful tap/placement | `HapticFeedback.lightImpact()` |
| Clear/merge | `HapticFeedback.mediumImpact()` |
| Big combo / milestone | `HapticFeedback.heavyImpact()` + a light double repeat |
| Breaking the high score | Double pulse (mediumImpact ×2 with an 80ms gap) |
| Death / error | A single `HapticFeedback.heavyImpact()` |
| Collecting a coin | `HapticFeedback.selectionClick()` |

Make `HapticsService.pulse(pattern)` a unified function that respects the Haptics setting and checks device support.

**c) Visual Juice Elements (mandatory):**

- **Screen shake**, light, on big events (combo/death) — small amplitude (2–6px) and short duration.
- **Particles / particle bursts** on clear/merge/coin collection (colored stars/circles flying out).
- **Squash & stretch** on every moving element (jump, placement, merge) — gives cartoon life.
- **Pop scale + bounce** via `flutter_animate` on buttons and appearing elements.
- **Confetti** on breaking the high score and on milestones.
- **Floating score text** that floats up and fades (`+120`, `Combo x3!`) on every reward.
- **A short glow/flash** on the element being interacted with.
- **Number/counter roll:** coins and points increment with a gradual counter animation rather than jumping suddenly.

**d) Colors (Vibrant Palette):**

- Use **exclusively** the saturated palette adopted in §3.14.0 (`Pal`) — no other colors and no washed-out pastels.
- High contrast between interactive elements and the background, and every element outlined with the dark border `#141428`.

### 3.9 Theme System, Mascot, and Shared UI

- `GameTheme`: each game gets a color palette **derived from `Pal` in §3.14.0** (Blocko blue/red, Dashy purple/pink, Mergo turquoise/orange) — the detailed tables are in §3.14.8.
- Fonts: **`Baloo 2`** (weight 800) via `google_fonts` for all headings and buttons — it delivers the required cartoon character.

- All motion via `flutter_animate` (bounce, pop, shake) — it delivers the sense of reward.

### 3.10 The Shared "Addiction + Ads" Engine (`GameSessionFlow`)

This is the unified pattern that **all three games must follow** when a round ends:

```
Round ends (Game Over)
      │
      ▼
Show GameOverDialog containing:
   • Score + Best (with Confetti if the high score was broken)
   • [Continue ▶ 🎬]  → showRewarded('revive') succeeds ⇒ revive the player (once per round)
   • [Double coins x2 🎬] → showRewarded('double_coins') ⇒ doubles the round's coins
   • [Retry]  → restarts immediately + maybeShowInterstitial('game_over')
   • [Home]   → to the menu (+ banner at the bottom)
      │
      ▼
Update: bestScore, coins, totalGamesPlayed, gameOverCounter++
Log analytics: game_over, ad_shown, rewarded_completed...
```

**Why does this create addiction + a high volume of ads?**

- **Instant retry with one tap** → rapid back-to-back sessions → repeated interstitial impressions.
- **Continue via rewarded** → exploits the player's desire not to lose their progress → high-eCPM rewarded.
- **Double coins** → an economic bait that drives watching an optional ad.
- **Breaking the high score + confetti + haptics** → a dopamine reward loop ("one more time").
- **Skins unlocked by watching an ad** → a permanent extra reason to watch rewarded ads.

## 3.11 Shared Economy & Store System (Gems Economy & Store) — generic, in `game_core`

> **This is a pivotal system: built once in `game_core` and serving all current and future games.**
> **Fixed (in game_core):** the full engine — wallet, earning, spending, store, cosmetic slots, UI, limits, persistence, analytics.
> **Variable (supplied by each app):** only the **gem's shape/name/color** (`CurrencySkin`), the **catalog content** (`StoreCatalog`), and the game-specific **cosmetic slots**.

### 3.11.1 Objectives
1. The player earns a small number of gems on every win/round.
2. They earn more **by watching ads** (doubling + gem packs) → this raises rewarded impressions.
3. A store that sells: **(a)** gem packs via ads, **(b)** new avatars/characters/skins/forms via gems.
4. The "earn → buy cosmetics → show off" loop creates a permanent reason to return and to watch ads.

### 3.11.2 The Abstract Skinnable Currency (`CurrencySkin`)
```dart
// game_core: src/economy/currency_skin.dart
class CurrencySkin {

```
> The engine does not know the gem's "shape"; it only renders `assetIcon`. Therefore the look of the points can vary freely per game.

**🔒 The gem is completely unified across the three games (a distinctive/Premium currency):** the same `gem.svg` file and the same color **`#E886FF`→`#9A2AE8`** with a dark border `#141428` — **neither the shape nor the color changes between games**, so the gem retains one strong identity. (This supersedes any earlier currency description.)

### 3.11.4 Earning System (Earning) — tunable per game
```dart
class EconomyConfig {
  final CurrencySkin currency;
  final int baseWinReward;                       // minimum per round
  final int Function(GameResult r) winReward;    // reward based on performance (score/combo/distance)
  final int doubleMultiplier;                    // = 2 via rewarded ('double_gems')
  final List<GemPack> gemPacks;                  // store packs via ad
  final DailyReward? dailyReward;                // daily reward (optional, raises retention)
  final EarnCaps caps;                           // anti-abuse limits
}

class GemPack {
  final String id; final int amount;
  final AcquireMethod method;    // AcquireMethod.ad (now) | iap (future placeholder)
  final String? badge;           // 'x2' | 'Best value'
  final Duration cooldown;       // between claims
  final int dailyLimit;          // daily limit for this pack
}

class EarnCaps {
  final int maxRewardedGemClaimsPerDay;   // e.g. 20
  final Duration globalGemAdCooldown;     // e.g. 30–60s
}
```
**Earning sources:**
| Source | Mechanism | Ad Placement |
|---|---|---|
| Win/round | `winReward(result)` automatically in `GameSessionFlow` | — |
| Round doubling | rewarded doubles the round reward | `double_gems` |
| Gem pack in the store | rewarded → `wallet.earn(pack.amount)` | `shop_gem_pack` |
| Daily reward | once/day (+ option to double with an ad) | `daily_double` |
| Milestone/achievement | reward on record numbers | — |

**Limits (mandatory):** respect `globalGemAdCooldown`, `dailyLimit`, and `maxRewardedGemClaimsPerDay`. Store `dailyClaims{date,count}` and `lastGemAdAt` in Hive and reset them daily. This prevents abuse and keeps eCPM/revenue healthy.

## 3.12 Daily Login Rewards System (Daily Login Rewards) — generic, in `game_core`

> **Goal:** a prize for **every new day the app is opened** → builds the daily-return habit (retention) and increases sessions and ads. Generic in `game_core`; the per-game variable = the prize values/content only.

### 3.12.1 The Mechanism
- On app open, `DailyRewardService` checks the date: if it is a **new calendar day** since the last claim → it shows `DailyRewardDialog` automatically after the Splash.
- **A 7-day streak** with escalating prizes; day seven = a **big prize** (a large gem pack or a rare cosmetic).
- Missing a day → the streak returns to day 1 (soft reset).
- After day 7 the cycle restarts (day 1 again), with the possibility of a higher prize cycle later.

### 3.12.2 Ad Doubling (a revenue driver)
Every daily prize has an optional **"Double the prize 🎬"** button → `showRewarded('daily_double')` ⇒ doubles the day's gems. A guaranteed daily source of rewarded impressions.

│  💜20  💜30  💜40  💜60  💜80 💜100 🎁BIG │
├──────────────────────────────────────────┤

## 3.14 "Juicy Game UI" Visual Design Language (mandatory for every screen)

> **Philosophy:** the UI must "feel like a game", not like an app — and the means to that is the **cartoon sticker style** locked in **§3.14.0** (a thick dark outline around every element + solid shadows + saturated colors). Inspired by winning references (Brawl Stars UI/UX, Harvest Haven, Domino Ocean, Void Conqueror, Pixel Party) **while preserving casual-game simplicity**. This section defines a **shared toolbox** in `game_core/theme` + `game_core/ui`, all of it subordinate to §3.14.0.

> **⚠️ Important — each game has a completely different style and identity, not merely different colors** (approved decision; **glassmorphism is never to be used**). Each game is inspired by a different winning Dribbble reference:
> - **Blocko → "Candy Squishy"** (inspired by Playful Pixel Party): bright and toy-like, panels with thick cream frames, puffy squishy green/gold buttons, and a Home screen that shows a preview of the board. Details in §4.0.
> - **Dashy → "Clash-style HUD"** (inspired by Neomodeon / Void Conqueror): a faceted blue/purple background, a rich top bar with two currencies and green "+" buttons, gold buttons with frames, **hexagonal icons**, rarity frames with 3D models, and a framed hero. Rich, and reads as an action game instantly. Details in §5.0.
> - **Mergo → "Clean + 3D Hero"** (inspired by Bang Studio): a **single explicit pastel background** + **one large glossy 3D model/mascot centered** + a two-tone bold headline + minimal text + a clean button. Modern, elegant, simple. Details in §6.0.
> The tools below are shared components; each game **dresses them** in its own style (Blocko cream and puffy, Dashy framed rich and dark, Mergo clean minimal with a hero model).

### 3.14.0 ⭐ The Approved and Locked Visual Style — "Cartoon Sticker" (Bold Outline / Sticker Style)

> ✅ **APPROVED — LOCKED.** This is the official visual style for all three games. **It may not be changed or softened**, and every other visual section in this file is subordinate to it. Any conflict between this section and any other section → **this section governs**.

> **This is the most important visual section in the file.** After studying winning Dribbble/Behance references (Brawl Stars UI/UX, Harvest Haven, Domino Ocean, Potion Pop Saga, Steam It!), it became clear that what makes a UI "feel like a game" instantly is neither gradients nor gloss — it is **the thick black outline around every element + saturated colors + a solid shadow**.

| ❌ Common mistake (soft/app-like) | ✅ Correct (game) |
|---|---|
| thin light 1–2px borders | **thick dark 3–5px border** (`#141428`) around **every** element: buttons, panels, icons, tiles, currency pills |
| calm pastel colors | **bold saturated colors**: red `#FF4D3D` · yellow `#FFD028` · green `#3ED367` · blue `#37B6FF` · purple `#A855F7` · orange `#FF7A2E` |
| blurred `blur` shadows | **solid shadow with no blur** `box-shadow: 0 5px 0 #141428` (sticker/3D feel) |
| text with a light outline | **puffy letters with a 6–7px black outline** + a colored shadow beneath them (`-webkit-text-stroke` + `paint-order: stroke fill`) |
| low contrast | **high contrast and a strong punch** |

**Mandatory rules:**
1. Every interactive or prominent element has a **thick dark border** — no exceptions.
2. Shadows are **solid** (offset with no blur) and use the border color itself — this is what creates the cartoon depth.
3. The logo = a **lockup**: puffy letters with a thick black outline + a colored shadow + a **ribbon** beneath it with a black outline.
4. Do not tone the colors down — saturated is correct in casual games.
5. The unified dark border color `#141428` (not pure black) gives better warmth.

> This style applies to all three games as the foundation, while the **layout and color palette** change according to each game's style (§4.0/5.0/6.0).

#### Approved Tokens (Design Tokens — copy them verbatim)
```dart
// game_core/theme/app_style.dart
class Ink { static const c = Color(0xFF141428); }        // the unified dark border color
class Pal {                                              // the approved saturated colors
  static const red    = Color(0xFFFF4D3D);
  static const yellow = Color(0xFFFFD028);
  static const green  = Color(0xFF3ED367);
  static const blue   = Color(0xFF37B6FF);
  static const purple = Color(0xFFA855F7);
  static const orange = Color(0xFFFF7A2E);
  static const pink   = Color(0xFFFF2D78);
  static const teal   = Color(0xFF12D9C0);
  static const gemA   = Color(0xFFE886FF);               // the gem (purple→pink gradient)
  static const gemB   = Color(0xFF9A2AE8);
}
class Bd { static const thin = 3.0, thick = 4.0, heavy = 5.0; }   // border widths
```

#### Flutter Implementation (the base recipe — use it for every element)
```dart
// sticker-style container: thick dark border + solid shadow with no blur
BoxDecoration sticker({required Color fill, double radius = 14, double border = 4, double drop = 5}) =>
  BoxDecoration(
    color: fill,
    borderRadius: BorderRadius.circular(radius),
    border: Border.all(color: Ink.c, width: border),
    boxShadow: [BoxShadow(color: Ink.c, offset: Offset(0, drop), blurRadius: 0)], // ⚠️ blurRadius = 0
  );

// logo text: thick black outline around the letters (two layers: stroke then fill)
Widget outlinedText(String t, {double size = 30, required Color fill, Color shadow = Pal.orange}) => Stack(children: [
  Text(t, style: TextStyle(fontSize: size, fontWeight: FontWeight.w800,
    foreground: Paint()..style = PaintingStyle.stroke..strokeWidth = 7..color = Ink.c
    ..strokeJoin = StrokeJoin.round)),
  Text(t, style: TextStyle(fontSize: size, fontWeight: FontWeight.w800, color: fill,
    shadows: [Shadow(color: shadow, offset: Offset(0, 5), blurRadius: 0)])),
]);
```
> **`blurRadius: 0` is a hard requirement** — any blur destroys the sticker feel instantly. And on press: reduce the offset to 2 + `scale 0.97` + haptic (§3.8).

### 3.14.1 Backgrounds
- **A rich gradient** in the game's color (vertical or radial) — see the table in §3.14.8.
- **Floating elements with depth:** small blocks/sparks/tiles/gems drifting slowly with a light blur (a background parallax layer).
- **Vignette:** soft darkening at the edges to focus the eye.

## 4. First Game — **Blocko** (Block Puzzle)

### 4.0 Style and Layout — "Candy Squishy" (inspired by Playful Pixel Party)

- **Background:** soft light blue with a subtle pattern / floating blocks, no heavy dimming.
- **Distinctive Home:** top currency bar; a **large central cream panel with a thick frame** showing a **live preview of the 8×8 board** (some colored blocks) + a "BEST" bar; below it **mode chips:** Classic (active) • Time; then a **puffy PLAY button** (gradient + cream frame + 3D bottom shadow).
- **Navigation:** cream rounded-square buttons (Shop / Settings) — no hexagons.
- Store / settings / dialogs: puffy cream panels and rounded chips in the same style.
> What sets it apart from the others: the brightness, the cream frames, and the board preview on Home.

### 4.1 Concept and Core Loop
An **8×8** grid. **3 pieces** appear (colored block shapes, similar to Tetris but fixed — no rotation). The player drags each piece onto the grid. When a full **horizontal row or vertical column** is completed, it is cleared and awards points. The run ends when **none of the three remaining pieces fits** on the grid.

**Why it's addictive:** no timer (relaxing "just one more"), simple yet satisfying spatial decisions, clearing multiple lines = a delightful combo. (Block Blast style — the most downloaded worldwide.)

### 4.2 Detailed Gameplay Rules
- The grid: a `List<List<int>>` matrix of size 8×8; value 0 = empty, >0 = color/skin identifier.
- The pieces: from a fixed set of shapes (1×1, 1×2, 1×3, 1×4, 2×2, 2×3, L, T, S, Z, corner...). Each piece has a color.
- 3 pieces appear in the "tray" below the grid. A new set does not appear until all three have been used.
- **Placement:** drag the piece over the grid; a ghost preview of the cells that will be filled is shown; placement is accepted only if all cells are empty and within bounds.
- **Clearing:** after each placement, check all completed rows and columns and clear them together. Multiple simultaneous clears = a **combo** (score multiplier + effect).
- **Scoring:** points for the placement (= the piece's cell count) + a clear bonus (= number of cleared cells × the combo multiplier) + a streak bonus (clears on consecutive turns).
- **Game Over:** if no remaining piece fits at any position on the grid.

### 4.3 Screens and UI Flow

### 4.5 Difficulty and Progression
- No levels; difficulty is self-generated (the fuller the grid, the harder placement becomes). Piece randomness is balanced: do not hand out 3 large pieces at once when the grid is full (weighted RNG to reduce early frustration — this raises retention).

### 6.1 The Concept and Core Loop
A **4×4** grid (or 5×5 as a harder mode). The player swipes in 4 directions; all tiles slide; **two equal tiles merge** into one of double the value. After each move a new tile appears (2 or 4). The round ends when **the grid fills up and no move is possible**.

**Why it's addictive:** the classic "one more time" loop, satisfying numeric progression, simple decisions with consequences. (The 2048 pattern, perennially popular.)

### 6.2 Detailed Gameplay Rules
- Grid `List<List<int>>` (0 = empty, otherwise the tile value 2,4,8,...).
- **Swipe:** four directions. All tiles slide until they hit the edge or collide; two equal adjacent tiles in the direction of movement merge once per move.
- **New tile:** after any valid move (one that changed the grid), spawn a tile in a random empty cell (90% chance of 2, 10% chance of 4).
- **Score:** the value of each merge is added to the score.
- **Game Over:** no empty cells and no merge possible in any direction.
- **No timer** (relaxing).

### 6.4 Controls

### 6.5 Difficulty and Progression

Calm, relaxing background music.

**Haptics:** lightImpact on every swipe, mediumImpact on merge, heavyImpact + a double pulse on a milestone or breaking the record, selectionClick on coins.

## 7.1 Step-by-Step Build & Publish (per app, both stores)

> **Core principle:** one monorepo → three fully independent store apps. Every command below is run **from inside a single app folder** (`apps/blocko`, `apps/dashy`, or `apps/mergo`). Each app has its own `applicationId` (Android) / `bundleId` (iOS), icon, name, version, store listing, and AdMob account — the shared code lives only in `packages/game_core`.

### 7.1.0 One-time monorepo setup
```bash
# from the repo root
dart pub global activate melos      # install the monorepo tool (once per machine)
melos bootstrap                     # link game_core into all three apps + run pub get everywhere
```

### 7.1.1 Per-app identity (set once, before first publish)
| Item | Blocko | Dashy | Mergo |
|---|---|---|---|
| Android `applicationId` | `com.mgames.blocko` | `com.mgames.dashy` | `com.mgames.mergo` |
| iOS `bundleId` | `com.mgames.blocko` | `com.mgames.dashy` | `com.mgames.mergo` |
| App display name | Blocko | Dashy | Mergo |

- **Android:** set `applicationId` in `apps/<game>/android/app/build.gradle`, and app name in `android/app/src/main/AndroidManifest.xml` (`android:label`).
- **iOS:** set `PRODUCT_BUNDLE_IDENTIFIER` in Xcode (or `ios/Runner.xcodeproj/project.pbxproj`), and `CFBundleDisplayName` in `ios/Runner/Info.plist`.
- **App icons:** generate per app with `flutter_launcher_icons` (add config to each app's `pubspec.yaml`, then `dart run flutter_launcher_icons`).
- **Version:** each app's `version:` line in its own `pubspec.yaml` (`1.0.0+1` → bump `+build` every store upload).

### 7.1.2 Android — build & upload (Google Play)
```bash
cd apps/blocko                                   # (repeat for dashy, mergo)

# 1) create an upload keystore ONCE per app (keep the .jks safe, never commit it)
keytool -genkey -v -keystore ~/keys/blocko-upload.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload

# 2) reference it in android/key.properties (git-ignored) and android/app/build.gradle signingConfigs

# 3) put the REAL AdMob App ID in android/app/src/main/AndroidManifest.xml
#    <meta-data android:name="com.google.android.gms.ads.APPLICATION_ID" android:value="ca-app-pub-XXXX~XXXX"/>

# 4) build the release App Bundle
flutter build appbundle --release
# output: build/app/outputs/bundle/release/app-release.aab
```
Upload the `.aab` at **play.google.com/console** → Create app → Production → upload. Fill store listing (title, description, screenshots, feature graphic, privacy-policy URL, data-safety form, content rating, ads declaration).

### 7.1.3 iOS — build & upload (App Store)
```bash
cd apps/blocko                                   # (repeat for dashy, mergo)

# 1) set bundleId + Team in Xcode (open ios/Runner.xcworkspace), enable automatic signing
# 2) Info.plist: GADApplicationIdentifier (real iOS AdMob App ID),
#    NSUserTrackingUsageDescription (EN+AR), SKAdNetworkItems
# 3) build the archive
flutter build ipa --release
# output: build/ios/ipa/*.ipa
```
Upload with **Transporter** app (or `xcrun altool`/Xcode Organizer) → then at **appstoreconnect.apple.com** create the app record, fill listing + privacy questionnaire + ATT declaration, and submit for review.

### 7.1.4 Switch test → real ad IDs (before publishing)
- Replace the Google **test** ad unit IDs (§3.5) with the real ones in each app's `GameConfig.adUnits` (per platform). This is the single switch that flips the app from test ads to revenue.

### 7.1.5 Ship-all helper (optional)
```bash
# from repo root — build every app's Android bundle in one go
melos exec --scope="blocko,dashy,mergo" -- flutter build appbundle --release
```

> **Reminder:** stores require a reachable **privacy-policy URL** and an **ads/data-safety declaration** for every app because all three serve ads. Prepare one simple privacy page and reuse its URL across the three listings.
